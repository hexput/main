- (decision) Hexput v2 is an open-source library/system-service (Redis-model: installed and run as a standalone daemon; apps connect over socket), not a SaaS product or internal-only component.
- (decision) v1 is being fully discarded — written when the author was inexperienced, has zero real users. v2 is a from-scratch, production-quality rewrite; no v1 constraints or code carry over.
- (decision) Differentiation vs WASM/OPA/Rhai/Extism/Deno-isolates: Hexput is a language-agnostic, centralized scripting runtime reached over sockets (not embedded per-process); user code is parsed/compiled once and AST-cached; host functions are reached only via capability-controlled bidirectional RPC; safety comes from multi-dimensional resource budgeting (CPU, memory, allocation count, RPC call count, output size, side effects) plus a transactional effect model, not from loop/instruction caps alone.
- (decision) Success = scalable stability (AST cache and similar robustness techniques keeping execution reliable under load) over raw feature count. Rhai is the only project considered performance-comparable; a public benchmark vs Rhai is planned.
- (decision) No rollback in v2 baseline (remote function calls have no automatic compensation). Future version may let host register a per-function rollback handler for optional compensation. Errors caused by the developer's own registered functions are explicitly out of scope for Hexput to fix.
- (decision) Connection model: two modes — fresh connection, or reconnect using a client id issued on first connect. No 1:1 constraint between id and connection; multiple backends can share/reuse a client id. Future: master-slave mode where slave daemons execute work routed by a master, enabling horizontal scaling.
- (decision) Deployment model: Hexput is NOT an embedded library — it is a standalone runtime service/sidecar, run via systemd or Docker. Same-machine backends connect over Unix Domain Socket for low latency; remote backends over TCP/TLS or WebSocket. The 'library' pieces that ship are thin client SDKs (Python, Node.js, etc.) for talking to the Hexput daemon, not the runtime itself.
- (override) Stakes reframed: this is not a generic internal team decision — Hexput v2 is the subject of the user's Master's thesis. Research question: can a capability-based, resource-budgeted scripting sidecar give a more predictable/safe execution model at lower latency than WASM sandboxes and traditional policy engines, for frequently-evaluated user-defined business logic? Contribution framed as unifying untrusted-code isolation, deterministic execution, resource metering, policy evaluation, and sandboxed plugin systems (usually studied separately) under one language-independent sidecar + capability-mediated bidirectional RPC architecture, studying the security-expressiveness-latency tradeoff.
- (decision) Brief audience is engineering-facing: future contributors, PR authors, and AI coding agents onboarding to the codebase — not the thesis committee. The thesis document itself is a separate artifact; this brief drives engineering/architecture work.
- (decision) No fixed timeline/deadline for v2. Benchmark plan accepted as proposed: compare vs Rhai, a WASM sandbox (Wasmtime/Extism), and a policy engine (OPA) on p50/p99 latency, throughput, cold-start/AST-cache-hit time, and memory footprint.
